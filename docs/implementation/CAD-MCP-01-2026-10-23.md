# CAD-MCP-01 — 모델과 독립된 CAD 연결

사용자의 “기능 추가보다 기능과 코파일럿을 연결하는 MCP가 먼저” 요청에 맞춰 기존 도구를 공식 MCP SDK의 stdio 서버로 연결했다. [설정·계약·한도](../architecture/CAD-MCP.md)는 대표 문서에서 관리한다.

## 바꾼 구조

기존 `cadToolContract`와 `createCadToolSession`은 공통 JSON 도구 계약이었다. 외부 MCP 클라이언트와 initialize/tools/list/tools/call로 연결되는 서버는 없었다. 이번에는 기하 구현과 별개로 아래 어댑터를 추가했다.

- `server/cadMcpServer.ts`, `mcpStdio.ts`: 공식 SDK 2.3.1, stdio 시작/검색/스키마 검증/호출/취소. 공통 CAD 스키마에서 도구를 생성하며 모델 전용 명령을 복제하지 않는다.
- `server/cadMcpBroker.ts`: Vite dev/preview의 편집기별 opt-in bridge. 서로 다른 UI/agent 토큰, loopback/Host/Origin 검사, 크기·시간·큐 제한, 연결 해제/취소 전달.
- `cadMcpRuntime.ts`: 캡처한 문맥을 기존 조회 세션에 연결하고 쓰기를 App의 동일한 native 미게시 Review에 전달한다.
- `useCadMcpBridge.ts`, `McpConnectionPanel.tsx`: 활성화/설정 JSON/연결 해제/최근 호출 표시. native 파일과 브라우저 영속 저장소에 토큰을 기록하지 않는다.
- `App.tsx`: MCP의 검증된 도구 호출도 내부 플래너/gateway와 같은 preview/Review/Apply로 처리한다. proposal receipt는 미게시·게시·취소를 구분한다. 모델 호출이나 remote Apply를 추가하지 않았다.

## 검증 과제

공식 SDK stdio 클라이언트가 실제 브라우저에 연결해 도구 목록과 문맥을 읽고, 호스트 문이 있는 벽과 연관 BRep 평면 절단을 하나의 제안으로 보냈다. UI Apply 전 CAD와 History가 그대로인지 확인했다. 두 번째 제안이 열린 Review를 덮지 못하며, 작업면 변경 시 이전 문맥·receipt가 취소되는지 확인했다.

새 문맥으로 다시 제안한 뒤 실제 UI Apply로 게시했다. MCP 측 실제 측정 체적이 `6000×200×3000 − 900×200×2100`과 일치하며, 단일 Undo가 원본 중심선·벽·연관 도면을 함께 제거하고 Redo가 identity를 복원했다. 이어 개별 쓰기 도구도 미게시 상태로 준비되는지, 연결 해제가 그 제안을 폐기하고 이전 프로세스의 조회를 막는지 확인했다. 이 흐름에 외부/로컬 모델 요청은 0회다.

공식 SDK 테스트는 실제 stdio 초기화·도구 검색·호출·취소를 사용한다. broker 테스트는 Origin/토큰/편집기 구분과 무효화/취소를, runtime 테스트는 문맥 변경/선택/기하·Undo 경계를 검사한다. 실제 실행 수치와 로그는 [검증 manifest](../verification/CAD-MCP-01-2026-10-23.json)를 따른다.

## 지원 범위

37개 공통 CAD 도구를 노출한 로컬 MCP 연결이다. 전체 수동 도구가 모두 노출된 것은 아니며, public HTTP MCP·OAuth·headless 실행·모델 추론 엔진은 이번 범위가 아니다. 미적·공간 설계 완성이나 이전 졸업 과제 미달 판정도 바꾸지 않는다. 이후 기능 확대는 공통 schema·조회·계획·검증·오류·Undo 계약을 먼저 연결하고 모델별 adapter에서 같은 실행 경로를 사용한다.
