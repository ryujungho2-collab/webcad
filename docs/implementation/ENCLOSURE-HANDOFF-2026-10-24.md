# 외함과 덮개의 사람 / 코파일럿 / MCP 작업 인계

센서 브래킷 다음 과제로, 120 × 90 × 40 mm 벽걸이 전자장치 외함과 3 mm 별도 덮개를 만들었다. 새 기하 기능 대신 부품을 오가며 같은 도구를 사용하는 흐름을 검증했다.

## 과제와 실제 실행

- 사람이 Shared tools 폼으로 120 × 90 × 36 mm 블록을 만들고, 내부 자연어로 높이 40 mm와 3 mm 셸을 적용했다.
- 실제 공식 SDK stdio MCP가 전면 Ø12 포트, 덮개 기둥 네 개(Ø8, 높이 37, Ø3.2 깊이 12의 막힌 구멍), 벽걸이 귀 두 개와 Ø5 구멍을 제안했다. 모든 제안은 기존 UI Review / Apply를 사용했다.
- 사람이 별도 덮개를 만들고 부품 대상을 바꿔가며 치수를 검토했다. MCP가 Ø3.5 구멍 네 개와 환기 슬롯 여섯 개를 가공했고, 사람이 같은 Boolean 폼에서 마지막 슬롯을 잘랐다. 슬롯은 모두 3 × 24 mm, 총 일곱 개다.
- 같은 부품 ID를 유지해 조립 위치(Z40)와 분리 위치(+160 X, −40 Z)를 오갔다. 실제 보어 원본 여덟 개의 BRep 측정으로 덮개/기둥 구멍의 XY 중심 일치를 확인했다.
- 최종 두 부품에서 실제 BRep 단면 세 개를 만들고 native / STEP / SVG / DXF로 내보냈다. Undo/Redo와 저장 후 재열기를 확인했다.

## 발견하고 고친 UX

기존 흐름은 부품 선택마다 Model tree로 이동해야 했다. Copilot → Shared tools → **Choose tool targets**에서 이름/ID로 검색하고 **Use target / Add target**으로 실제 편집기 선택을 바꿀 수 있게 했다. 검색 자체는 문서나 선택을 바꾸지 않으며, 명시적으로 대상을 바꿀 때 미적용 제안을 취소한다. 같은 선택을 재확인하면 진행 중인 검토를 유지하며 선택 초기화는 실제 선택을 지우고 검토를 취소한다. 같은 선택을 캔버스, 자연어, MCP가 사용한다. MCP에 원격 선택 권한을 추가하지 않았다.

선택 목록에는 실제 이름과 ID, 순서가 표시된다. 두 대상은 **Swap target and tool**로 순서를 바꿀 수 있고, 제거/초기화도 같은 선택 상태에 반영된다. 후보는 기존 `selectAllIds` 규칙의 보이고 잠금 해제된 root 대상으로 한정한다. 숨겨진 소비 원본은 조용히 선택되지 않는다. 최대 50개 후보를 보여주며 검색으로 좁힌다.

치수 폼은 부품·치수 키·실제 값이 바뀌면 현재 값을 불러온다. 이전 부품의 제안값이나 잘못 입력한 값이 새 부품에 남지 않는다. 대상 변경 시 이전 입력 오류도 지운다. 폼 입력과 선택은 기하 실행기가 아니며 기존 `validateCadToolCalls` / captured session / native preview / Apply 경로를 유지한다.

## 재현과 범위

`apps/web`에서 `node scripts/browserChecks.mjs --page=enclosureHandoff --artifacts`를 실행한다. 물리 브라우저 입력과 실제 MCP SDK를 쓰며 CAD 문서를 직접 조작해서 과제를 만들지 않는다. 모델 API 요청은 0회다. 치수와 도구 순서는 에이전트가 구성했다.

외함의 독립 체적 기준은 `81048 + 2074.62π mm³`, 덮개는 `30888 − 36.75π mm³`다. 체적만으로 위치가 올바르다고 판단하지 않으며 별도 보어 중심·조립 경계 측정도 수행한다. 표준 체결부품, 나사산, PCB/배선 배치, 방수·열·구조 성능이나 제조 적합성은 검증 범위가 아니다. 단면은 실제 절단 형상이며 치수·공차가 갖춰진 제작도라고 부르지 않는다. 전체 수동 도구의 MCP 연결도 여전히 완료되지 않았다.

산출물은 `output/projects/instrument-enclosure`에 있다. native 원본에는 기하, 숨긴 원본, 마감과 연관 단면이 남는다. `handoff.json`에는 MCP 제안과 적용 영수증이 있으며 연결 토큰은 기록하지 않는다.
