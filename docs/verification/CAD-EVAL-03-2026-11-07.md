# CAD-EVAL-03 — Loft Connection and Source Preservation

2026-11-07. **Native에서는 가능하지만, 현재 일반 Copilot 경로는 모델 호출 전 차단됐다.** 모델의 설계 실패/성공을 판정한 실행이 아니다. 실제 모델 추론 0회, Editor Apply 0회. 같은 차단이 두 번 발생한 뒤 추가 시도나 제품 수정 없이 종료했다.

## 다른 종류의 과제

앞선 scalar 폭/지름 변경 대신, 기존 3단면 로프트의 연결 방식을 바꾼다.

- 원형 단면: XY 평행면 Z=0/30/60 mm, 반지름 20/10/25 mm.
- 기존 형상: 세 단면을 순서대로 잇는 `ruled: true` 로프트.
- 요청: 기존 smooth interpolation으로 전환한다.
- 보존: 단면 정의/고도/순서/끝단 프로파일/live 관계, 기존 객체 ID와 월드 배치 [70,40,10], 마감, 다른 보호 블록 및 그 원본.
- 금지: 원본 단면 변형, scalar 치수 변경으로 대체, 새 객체로 재생성, 자동 Apply.
- 미확정: 재료·제조 공차·유동·하중. `ruled:false`를 G1/G2 연속성이나 성능 인증으로 해석하지 않는다.

합성 문서는 객체/피처 각 5개이며 최종 BRep은 로프트와 보호 블록 2개다. fixture는 기존 Native 도구로 준비했다. AI 전체 형상 생성으로 집계하지 않는다. 기존 `DesignStudy` 형식의 의도는 평가자가 작성했다.

## 실행 결과

| 시도 | 요청 조건 | 모델 추론 | Native 모델 제안 | 최종 결과 |
|---|---|---:|---:|---|
| 1 | 한국어 요청 + 기존 의존성 그래프의 세 live 엣지 | 0 | 0 | `CONTEXT_BUDGET` 사전 거부 |
| 2 | 같은 보존 의도의 간결한 영어 요청 + 출처/문서/세 source ID/live 요약 | 0 | 0 | 같은 `CONTEXT_BUDGET` 사전 거부 |

예정 모델은 기존 로컬 Ollama `qwen3-coder-32k:latest`였고 연결 상태 점검은 성공했다. 그러나 `/api/chat` 호출은 한 번도 발생하지 않았다. 실제 입력/유지/출력 토큰은 미측정이며 0 토큰의 성공 실행으로 기록하지 않는다.

첫 시도 runner 3.218초, 두 번째 2.930초다. fixture·대조안·SVG 생성까지 포함한 시간이며 모델 지연 시간이 아니다. 전송 전 모델 요청을 만들던 Gateway가 종료했다. 두 실행 모두 source hash 전후 동일, editor document/History 불변, `preview.webcad.json` 없음이다.

### 최초 차단: Gateway 입력 예산

`apps/web/server/localCopilot.ts:113`의 기존 검사:

```ts
if (!v.task && utf8Bytes + 256 > numCtx - outputReserved) throw Error("CONTEXT_BUDGET: conservative UTF-8 input ceiling exceeded. Narrow tools/results; no inference sent.");
```

일반 요청의 설정 `numCtx=16384`, `outputReserved=1024`에서 system/user 내용의 UTF-8 바이트 합이 15,104를 넘으면 거부한다. **바이트 수는 토큰 수가 아니다.** 이번 결과를 엔진의 실제 토큰 초과/입력 잘림으로 단정하지 않는다.

저장된 클라이언트→Gateway 요청 JSON은 각각 14,033/13,439 UTF-8 bytes였다. 이는 Gateway가 자체 카탈로그·근거 안내·system 지시를 넣어 구성하는 최종 모델 messages의 크기와 다르다. 두 요청 모두 최종 사전 검사에서 거부됐다는 사실까지만 확인했다. 한도를 늘리거나 검사를 우회하지 않았다.

### 별도로 확인한 차단 조건: 편집 도구 라우팅

이 모델 요청은 기존 `taskToolScope`에서 `general`로 분류되며, 실제 요청 카탈로그의 13개 도구에는 **`solid.loft.update`가 없다**.

- 실제 명령: `apps/web/src/state/commandBus.ts:792`, `update-loft`.
- 실제 도구 계약: `apps/web/src/copilot/cadToolContract.ts:103`, `solid.loft.update`.
- 실제 planner: `apps/web/src/copilot/cadModelingTools.ts:49`, 입력/선택/live/no-op 검증 후 명령 생성.
- 일반 Copilot scope: `apps/web/src/copilot/copilotTaskScope.ts:3` 및 `apps/web/server/localCopilot.ts`의 server-owned scope 재구성.

따라서 입력 예산만 통과시켜도 현재 카탈로그는 이 편집을 모델에 제공하지 않는다. 이는 코드와 요청 카탈로그 대조 결과이며, 모델이 도구를 잘못 골랐다는 증거가 아니다. 이번에는 실제 모델의 미지원 설명/추가 질문 능력도 실행되지 않았다. scripted clarification 테스트와 실제 모델 응답을 혼동하지 않는다.

## 독립 Native 대조

기존 `createCadToolSession.plan([solid.loft.update])`와 `prepareCadCommand`로 대조안을 실행했다. 일반 Copilot 카탈로그를 우회한 **평가자 Native preflight**이며 AI 실행으로 세지 않는다.

- `ruled:true` 체적: **52,621.676947629036 mm³**.
- `ruled:false` 체적: **40,623.705017269036 mm³**.
- 차이: **11,997.97193036 mm³**.
- 두 BRep 모두 Native validity `valid`.
- 단면 원본·순서·live 엣지 3개·객체·배치·마감·보호 블록·기타 문서 상태 유지.
- Native 직렬화/역직렬화 왕복 통과.
- **9/9 criterion 통과**. 단순 flag 변경을 실제 형상 변경으로 오인하지 않도록 Native 체적 변화도 요구했다. 체적 차이를 일반적인 곡률/연속성 검증으로 주장하지 않는다.

## 후속 판단

**CAD 자체 기능 부족과 Copilot 접근 부족을 구별할 수 있는 과제**가 추가됐다. 이 과제를 실제 모델 능력 평가로 진행하려면 (1) 검증된 선택 loft에서 기존 편집 도구를 노출하는 task routing, (2) 일반 카탈로그·요청의 예산 내 구성 두 조건이 필요하다. 새 커널이나 loft 기능은 필요하지 않다.

후속 수정·다른 과제·모델 교체는 자동 시작하지 않았다. 앞선 장착판 성공과 통풍 실패도 그대로 유지한다.
